## Executive finding

OutreachFlow is a coherent **local research-first workflow prototype**, with genuinely useful discovery/triage and separation between unverified indexed evidence, owner verification, and outreach decisions. The most consequential next work is **data/recipient/message identity correctness** rather than additional UI or more LLM features. It currently has no real outbound sending implementation, no unattended follow-up runner and no production-ready migrations/recovery.

### Runtime boundaries and architecture

```text
Blazor Interactive Server / account HTTP endpoints
   |-- ASP.NET Core Identity + Google auth (openid/email/profile)
   |       \-- AccountDbContext SQLite: users, logins, memberships, active workspace
   |-- IWorkspaceAccess: server-resolved authorized active workspace
   |       \-- OutreachDbContext SQLite: workspace, prospects, evidence, messages, activities
   |-- Discovery: configured workspace profile -> 2 bounded Tavily basic searches
   |       -> keyword rank + deterministic triage -> owner-reviewed route to prospect
   |-- Research: public site -> robots -> bounded same-site SSRF-guarded HTML fetch
   |       -> optional isolated Playwright rendering -> unverified evidence/contacts
   |-- Prospect workflow: human research decision -> draft -> simulated OR owner-attested
   |       external send/reply -> manual tasks, warm lead, application or suppression
   |-- Mailbox: separate gmail.readonly OAuth consent -> protected local refresh token
           -> bounded user-initiated Gmail inbox previews -> reviewed inbound import
```

### Positive design choices worth retaining

- Search costs and page research are bounded; no autonomous mass crawling or LLM is hidden behind a click.
- A search result, published email address and discovered portal remain **unverified** until owner action.
- The crawler checks DNS resolution at connection time, redirects, response sizes, robots hints and localhost/private-network restrictions; browser research is opt-in.
- Identity separates Google login from restricted Gmail read consent; Google first-signup gets its own workspace, existing local users link explicitly rather than by email string.
- Workspace IDs come from server-side membership checks; exports and prospect detail lookups are scoped.
- Gmail refresh tokens are protected in local Windows development using DPAPI-backed ASP.NET DataProtection, and excluded from Git.
- There is no active real mail sender: `IOutboundEmail` resolves to `DryRunEmail`.
- Offline smoke tests cover substantial logic, positive/negative routing and cross-workspace access; CI also boots the localhost site and checks unauthorized redirect.

### Detailed code implications

**Identity / bootstrap:** `AccountEndpoints` first-owner POST historically called `FirstAsync` on seeded `Workspaces`. That hidden dependency is being removed in PR #12. `GoogleUserProvisioner` writes two different SQLite databases without one atomic transaction; best-effort cleanup exists but can leave inconsistent data on fault. Google sign-in verifies stable subject identity and does not silently merge by email; this should be preserved. Member role is stored but granular authorization is not yet broadly enforced beyond Gmail-owner operations.

**Data model:** `Prospect` conflates company/site account, contact, lead process, and campaign state. `OutreachMessage` lacks provider/thread identifiers and one-to-one unique inbound/outbound claims. `ActivityEntry` uses string-based type/detail, so idempotence is operational rather than schema-enforced. `Prospect.WorkspaceId = 1` remains a legacy compatibility default needing migration, not a tenant-safe long-term convention. Reference and audit rows are tied indirectly through prospect ID; cross-tenant children assume parent authorization is correct.

**Discovery:** query planning and ranking are explainable and affordable, but they primarily discover public procurement processes rather than private businesses with fleets. Relevance scores are keyword matches only; the classifier is intentionally heuristic. URL-based reviewed import lacks DB uniqueness and robust canonical organization identity. The app-wide usage ledger is single-process and shared across workspaces, not a metered tenant service.

**Research:** `ResearchUrlPolicy`, `OfficialSiteResearcher` and `PlaywrightHtmlBrowserRenderer` have meaningful safeguards but are not production security sandboxes. Cross-site linked portals are evidence, not fetched verified processes. HTML/contact extraction uses bounded regex; source content quality is uncertain. Real-world false-negative/JS-shell behavior is recorded as inconclusive rather than as a missing process.

**Prospect lifecycle:** `OutreachService` combines research, contact review, draft rendering, simulated sending, owner-attested sending, actual reply entry and export in one ~580-line service. Its domain transitions need explicit testable invariants before adding real sending; PR #12 addresses the most immediate silent-reopen paths.

**Gmail:** `GmailMailboxService` stores workspace encrypted refresh tokens and checks sender-email match to workspace settings. It can review a bounded list and manually import candidate reply text, but does **not** confirm Gmail thread relationship to a real sent provider ID. A new email from a previous contact could be mistaken for a reply. Manual review is a required safety control; provider-ID uniqueness, bounded MIME responses and refetching rules need strengthening.

**Tests/CI:** offline checks cover approximately 100 assertion/helper call sites over 910 lines and recent main runs pass. They do not prove human OAuth consent, database restore, actual Gmail import against a real recipient, parallel duplicate imports, a production deployment or hostile browser sandbox. Existing PR #6 conditional CI steps are obsolete and removed in the cleanup PR.

**Documentation:** current `README` and `ROADMAP` at audited head describe earlier branch states, contradicting merged code. This report, the updated README and revised roadmap should be the current authoritative baseline; historical PR-specific notes remain for provenance.

6. Only plan hosted beta after auth, browser, privacy, quotas and recoverability gates (#16, #17, #19, #20, #22) succeed.

## Definition of done and stage position

- **Stage A — research MVP:** functioning now, with real work still requiring user judgment.
- **Stage B — Google login and read-only inbox connection:** merged, provider connection verified by owner; end-to-end inbound record not yet demonstrated in live acceptance.
- **Stage C — one reliable real provider message with one reliably correlated reply:** not implemented; this is the immediate engineering goal.
- **Stage D — safe unattended 1–2 follow-up sequences for 5–10 approved accounts:** not implemented.
- **Stage E — public multi-tenant SaaS:** not implemented; depends on security, privacy/provider verification, migration, backup, recovery and support.

For approximate engineering planning, a focused real-message and persistence slice is **roughly 2–4 engineering weeks** for one developer, with durable automation plus a controlled pilot **another 2–5** depending on provider failure modes and testing. These are **non-binding planning ranges**, not release promises. Google restricted-scope approval and public hosting can materially lengthen the schedule.

**Bottom line:** the existing codebase is a promising, useful local research tool, but **not an automated outreach product yet**. The next milestone should build a verifiable, idempotent communication loop before increasing autonomy.
